# Telegram paired-browser remote

Scope: read when the task touches the Telegram "Open session" link, paired-browser (PWA) control of UI-driven root sessions, the gateway's browser HTTPS origin or loopback companion listener, the gateway Host allowlist, or setup and recovery of a phone browser.
Authority: Authoritative
Last-verified: 2026-11-02

Implemented and accepted by the owner for the Dev build with Safari on iPhone, with the limits listed below. Telegram event rules (eligibility, lineage, question audience, terminal order) stay owned by the [Telegram attention notifications contract](plans/2026-10-10-telegram-attention-notifications-contract.md). Code and tests are the behavioral source of truth.

## Invariants
- **No MCP handover.** A gateway app-link caller acting on a session that passes the notifier's `isAttentionNotificationRoot` uses the desktop's session-targeted respond, steer and cancel paths (`AgentModeViewModel+RemoteRootControl.swift`). It never installs MCP control, so the session keeps sending later alerts, including the completion of a phone follow-up. Ordinary MCP callers keep their existing rules. Phone sends to a not-yet-loaded session and native control-plane commands such as `/compact` or `/goal` are refused; use the Mac for those. Tool/edit approvals and Codex `requestUserInput` remain outside phone control.
- **Browser identity.** A non-extractable P-256 key and device record are stored together in one IndexedDB transaction, keyed by the gateway's `/healthz` `channel` (`release` or `debug`). Each build has its own paired-device list and host key. Pairing uses discovery (nonce + channel), the Mac's fingerprint approval, one-use tickets and signed frames.
- **Host allowlist.** HTTP routes and the WebSocket upgrade accept only a single `Host` matching the bind address, the accepted socket's local `ip:port`, or the browser origin's authority (`GatewayHostAllowlist.swift`). Forwarded headers are never trusted.
- **Origin and transport.** The browser origin is `https://<MagicDNS name>:<browserHTTPSPort>`, derived from Tailscale status. There is no typed origin. While an origin is published, the gateway also listens on `127.0.0.1:<gateway port>` for Serve. Direct access over the Tailscale IP stays in place. The link contains only the origin and `?session_id=<uuid>`, so it grants nothing without a paired browser.
- **Telegram button.** Part 1 of a completion or question alert gets an "Open session" URL button only when `browserHTTPSPort` is set and the gateway is running and ready. Otherwise the alert is text only.
- **Phone UI.** It has the following parts:
  - a structured question form (options, multi-select, custom answer, skip);
  - one auto-growing text box with its send button, labelled Steer while running and Follow up when idle;
  - Stop in the sticky header, apart from Send, shown only while the session is running or waiting;
  - a compact Top / Latest pill right after the transcript. It is `position: sticky` at the bottom of the screen while the transcript is read and settles after the transcript's end, so it never covers the question form or the composer. Top lands the start of the loaded transcript ("Load earlier messages" while older turns exist) under the header and never fetches older pages. Latest goes to the end of the page, where new output is followed again; while older pages are loaded, it first returns to the newest page as Refresh does (older pages are dropped), since background refresh is paused there;
  - session rows that are buttons;
  - an Activity log that starts collapsed.

  The composer keeps Send to the right of the auto-growing text box at phone width (the box can shrink, `min-width: 0`).

  The Connection panel stays visible. The page follows the system's light or dark appearance, uses 17px system text (16px minimum in fields, so iOS does not zoom) and 44px controls, respects safe areas and keeps browser zoom. It scrolls as one document, with no nested transcript scroller, and the composer sits in normal flow at the end of the session view. Agent and server text reach the page only through DOM text APIs; `PWAResourceTests` bans markup-parsing and eval APIs.
- **Transcript presentation.** `get_log`'s `transcript_xml` writes role bodies and tool arguments unescaped, so it is never handed to an XML or HTML parser.
  - `segmentTranscript()` in `app.js` is a conservative forward line scan. It recognizes only the serializer's own record lines and has these rules:
    - a close tag counts only at a line end followed by another record line or the end of input;
    - a candidate inside a backtick-fenced example in the body is not a close;
    - the serializer cuts only grouped system summaries and tool arguments, so there a fence-hidden candidate ends the record as raw text and later records are scanned normally;
    - in other bodies, a fence-hidden record is kept only when a later close follows outside the fence, before any same-type opening line and the next unfenced record line; otherwise it shows raw up to its first candidate, so an interrupted fence never swallows later records;
    - unknown or uncertain text, including a record that never closes, stays visible verbatim, and uncertain text is never given a role label;
    - the segments' raw text joins back to the input exactly;
    - bodies are never entity-decoded, and tool names are decoded from the serializer's four attribute escapes.
  - The primary view shows You, Agent, System, Error and Note sections, one collapsed disclosure per tool call with arguments, and complete code fences as code blocks with their language label and a Copy button; long code lines scroll sideways inside the block. Copy writes the exact code with the Clipboard API; without clipboard access (a plain-HTTP origin or a refused write) it selects the code for the system Copy menu and says Selected; when neither works it says Not copied, so it never reports a copy that did not happen. Its accessible name names the block ("Copy (swift code)"). Whether iOS offers the system Copy menu for a scripted selection is unverified; HTTPS is the normal origin.
  - Bodies render basic Markdown with DOM element and text-node construction only (`appendBody`, `appendMarkdown`, `appendInline` in `app.js`): paragraphs keep their line breaks; ATX headings; bullet and numbered lists, nested by indentation, with a numbered list's first number kept; `code` spans, which take precedence: emphasis text may contain only complete single-backtick code spans, so it never opens or closes inside code; `**`/`__` strong and `*`/`_` emphasis, with underscores not inside words. Inline markup never spans lines, and inline formatting is skipped on lines over 2000 characters; block recognition still applies. List continuation lines lose indentation only up to their item's text column. Links, images, quotes, tables, rules, HTML and anything else stay literal text. A blank line ends a list, so a list with blank lines between items shows as consecutive lists. An unmatched fence keeps itself and the rest of the body literal, with no Markdown. There is no syntax highlighting. This is a basic subset, not CommonMark: mixed emphasis delimiters and deeply list-indented fences can render imperfectly; the Raw transcript remains available.
  - The exact page text stays in a closed "Raw transcript" disclosure.
  - Known limit: exact record-shaped text outside a code fence can be attributed to the wrong record, though no text is lost. The serializer's grouped "Explored codebase" system summaries can cut a fence off unclosed, so such a row shows as raw text. The same cut applies to a complete fenced example of record lines inside a summary or tool arguments, and an example cut short this way in any body can have its remaining lines shown as records. In other bodies, a fenced example that holds a record's close line followed later by an opening line of the same type shows the whole message as raw text; it stays visible and is not mislabelled.
  - Records keep their DOM nodes, and so their open disclosures and focus, only when their position establishes the same occurrence: the view still starts at the same turn (matched from the start), or older pages were prepended to an earlier start (matched from the end). Whenever the start turn moves forward (the newest window rolls, or Refresh drops older pages), every record gets a fresh, closed node, even for identical text, since `get_log` carries no row identities. Disclosures open in the old nodes close at that point. A session switch discards all nodes.
  - The view re-renders when its text or its start turn changes; the start turn alone decides "Load earlier messages". Scroll is measured once before any layout write (Load earlier, raw text, records) and corrected once after them. A session view's first records land on the newest output, or on the question when the agent is waiting, unless the reader is typing or using a disclosure (focus in a hidden element does not count). Afterwards, new output is followed only when the reader is within 48px of the bottom and is not typing or focused in the transcript. Otherwise an anchor keeps its screen position: a focused, on-screen composer or question field first, else the first visible block whose node survived; with neither (as after a rolled window), the document position is kept. Sending does not scroll.
- **Transcript paging.** Pages are oldest-first: the newest page starts at `max(0, total_turns − 200)`, and "Load earlier messages" prepends the 200 turns before the oldest one shown. Background refresh pauses while older pages are loaded, and Refresh returns to the newest page. Newest-page loads coalesce overlapping refreshes and make at most one corrective page request; a turn added during that second request can appear on the next refresh.
- **Revocation.** A phone revoked on the Mac is disconnected within about 15 s (the gateway's trust-refresh loop). After that, ticket requests are refused and the page tells the user to pair again. The owner accepted the delay; there is no per-action re-check.

## Workspace chooser (implemented; live acceptance pending)
The sessions list no longer depends on one Mac window being open or on the connection's window binding.
- **Discovery.** `list_workspaces` is a read-only, gateway-owned frame in the client frame set. It requires `sessions:observe`, is not mutating, and is protected by passkey access like any list (withheld while locked, and settled as `passkey_locked` if a lock lands while its app read is in flight). It takes no arguments: any nonempty payload gets `invalid_payload` before any app call. Each request makes one fresh `bind_context list` read through the existing eligible-window helper and returns `{windows:[{window_id, workspace_id, workspace_name}]}`. An authoritative empty window list returns `windows: []`. Every other failure returns the fixed `workspace_discovery_unavailable` / "Open workspaces are unavailable. Retry." with no details and no cached fallback. A frame type the gateway doesn't know (an older gateway) shows a reload-or-update message instead. On the Mac, the read never opens, focuses or binds a window or workspace. The gateway's own binding-state refresh may still record a link as bound when exactly one window is open, but that is gateway-side bookkeeping only.
- **Selection.** The chosen workspace ID is kept in page memory only (not storage, the URL or the service worker). Entry to the sessions list (reload, reconnect, unlock, Back) rereads workspaces. A remembered ID that is still open is kept. A sole workspace is auto-chosen only before any choice. A remembered workspace that closed shows the picker rather than choosing another. With nothing open, the page shows "No open workspace is available" with Retry and sends no list. **Switch workspace** always rereads and shows the choices. Dismiss keeps the current choice. A failed Switch keeps the current list. Switch and recovery rereads clear the old choice rows first, so no stale row is offered while the page is looking. An entry reread over an already visible picker leaves its rows, but tapping them does nothing because they belong to an older generation. Before a reply arrives, a chosen workspace shows "Sessions not loaded yet." rather than an empty-workspace message.
- **Normalization.** Choices are deduplicated by `workspace_id`, so two windows of one workspace give one choice. The first nonempty name in ascending `window_id` order wins. Rows without a string ID are not choices. Choices are sorted by name, then ID. Missing or repeated names get a short ID suffix, in both the picker and the current-workspace label. The label keeps the suffix while a Switch has cleared the choices (Dismiss, a failed Switch, Refresh).
- **Listing.** `list_sessions` sends only `{workspace_id, limit: 50}`: never the name, so a rename cannot cause a combined ID+name mismatch. An accepted reply replaces list membership, and a rename in its `workspace` metadata updates the label. `workspace_not_open`, `workspace_mismatch` or `binding_required` from the chosen list clear the choice and reread once. Other list errors show a fixed retryable message. After the last Mac window closes, a scoped list keeps its existing lookup-unavailable mapping (`app_tool_error`), so Refresh shows "Sessions are unavailable. Retry." and keeps the choice. **Switch workspace** rereads and shows the no-open-workspace chooser. Mapping that case to `workspace_not_open` was deliberately not done: the desktop remote sidebar reacts to `workspace_not_open` by auto-opening the workspace on the host, and that existing client behavior is preserved.
- **Fences and isolation.** Discovery and list replies apply only under their own generation, socket, access generation and view generation, so older, post-lock or post-navigation replies do nothing; a reply that settles after the owner opened a session never shows the chooser over the detail or starts recovery. Watch frames update the page only for listed sessions or the open session, and never add list membership. Switching sends no `unsubscribe`, because another tab may share the device-wide watch. Earlier observations remain until normal cleanup. Only this flow opens the chooser; binding errors from other commands no longer open a global overlay.
- **Lock and links.** Lock clears workspace names, choices, picker DOM, the label and list membership; only the opaque ID survives, to be revalidated after unlock. An identity reset also forgets the ID. When a disconnect lands while the page is looking for workspaces with passkey protection off, the chooser is hidden. A newer chooser opened on a new connection is never hidden by an older failure. Deep links open their session directly without discovery. Typed composer and question drafts are snapshotted when leaving a session for the list, so they survive Back, Switch workspace and reopen without being sent. A steer that succeeds while its session's composer is still in the page clears the composer only if it still holds exactly the sent text, including after Back and reopen. Edited text and other sessions' drafts stay.
- **Evidence.** Wire, scope, runtime, bound and unbound (`binding_required`) two-window integration (discover, ID-only list, subscribe, steer, with no bind, open or focus), passkey E2E and JavaScriptCore PWA fixtures cover this behavior. Live iPhone Safari use with two Mac windows is not yet checked.

## Passkey unlock (implementation in progress)
The [optional passkey-unlock plan](plans/2026-10-31-remote-passkey-unlock-spec.md) adds user verification for already paired browsers. Steps 2–4 implement the app-owned verifier, policy persistence, enrollment/recovery coordinator, principal-only ceremonies, Mac controls, gateway enforcement and phone unlock flow. `Vendor/SwiftWebAuthn` and `Vendor/SwiftCBOR` retain pinned sources, localized validation fixes and licenses; provenance and limitations are in `Vendor/SwiftWebAuthn/PATCHES.md`. WebAuthn is linked into the app and tests, never the gateway. Software-signed fixtures and malformed-input tests do not establish live Safari/1Password compatibility.

- **Durable policy:** registry/records use schema 2 at the existing channel-specific filename. Valid v1 migrates to protection off in memory; subsequent saves write only v2. Unknown/malformed policy fails closed. Older app builds freshly reading v2 refuse it; recovery is a compatible build, not deleting registry files. The supported model is one app instance per channel; already-running old cached writers are not retrofitted. Policy/credentials survive ordinary metadata updates and re-pairing; security changes advance the epoch. Secure temporary-file replacement is the save commit point.
- **App ceremonies:** Mac authorization opens a 120-second enrollment window; one-use challenges last at most 60 seconds, bounded by that window. The app validates required user verification, ES256, exact origin/RP/credential bindings and post-await context. Registration stores only verified public material and never unlocks. Assertion verification creates no durable grant or counter-growth requirement. Reset remains required; Turn Off explicitly restores pairing-only policy.
- **Compatibility and status:** Enable/Enroll live-check a compatible gateway principal. Settings distinguishes persisted policy from the exact issued trust snapshot acknowledged after gateway enforcement barriers. Gateway principals retain the credential generation authenticated before asynchronous admission; rotation cannot restamp an old admission as current. Required or unreadable policy adds a mandatory launch-version argument that an old gateway rejects before listening. The new gateway requires a strict capability-1 snapshot, with no legacy permissive fallback.
- **Gateway grants:** process-local grants are shared by the paired browser across tabs and authenticated reconnects. Restart loses grants. The owner chose **30 minutes idle**, not an absolute cap. Only an explicit signed foreground-activity report with the current grant/epoch/lock references can renew, after its own fresh principal trust refresh and before the old deadline. Renewal uses captured activity time plus 30 minutes, at most one attempt per device per 30 seconds and one in flight; there is no trailing timer. Polling, rendering, watch traffic, metadata refresh and reconnect do not renew.
- **Enforcement boundary:** signatures and counters precede protected-command admission; queued work rechecks its original binding and current access. Every protected outbound enqueue checks the monotonic deadline on its NIO event loop. Lock notices follow the transition's cross-tab barriers and are revision-fenced. Withheld correlated results become generic lock errors, passive updates are dropped, and uncertain actions are never automatically retried. Bytes already queued or delivered cannot be recalled. Existing developer static-token connections close, and new ones are refused, whenever any device requires protection or trust is invalid/unavailable.
- **Trust and outages:** policy/reset/revocation normally arrive through the existing approximately 15-second refresh; enforcement begins when applied, not at the Settings click. Positively identified transport outages preserve the last valid policy and original grant deadline without renewal. The pinned MCP SDK conflates some response and transport failures, so ambiguous failures conservatively invalidate trust and close **all** paired connections, including policy-off browsers, plus static connections. Valid trust permits reconnect but does not resurrect removed grants. There is no strict reset/revocation-delay guarantee during an outage.
- **Browser wire contract:** access state comes from `hello_ack.access` and `lock_state`, not ceremony completion. Notices may arrive before hello or before/after completion; duplicate unchanged notices should be ignored and `reason` is advisory. Fresh same-kind begins replace pending ceremonies, so a client must not prefetch another begin while completion is outstanding. Registration never grants access and reconciles enrollment through a fresh trust read. Policy-off Lock is a no-op without an acknowledgment. The PWA consumes authoritative access metadata and keeps ceremony completion separate from permission to show content.
- **Bounded limits:** concurrent begins from different tabs can reach the app out of order and require retry. A subscribe admitted before Lock can retain its device-wide observation intent even when its response is withheld; deferred validation is discarded and the final sink still gates delivery. Tests establish real gateway/real verifier software-credential fixtures, not live Safari/1Password behavior; exact cross-loop barrier and mid-hello race fixtures remain limited.
- **Phone flow:** the page offers Unlock, Mac-authorized Set up passkey, Lock and Mac-recovery states. It prefetches options and calls native WebAuthn directly from the tap; cached options expire after 45 monotonic seconds, within the app's 60-second challenge limit. Registration is followed by a separate assertion. Lock and required-mode disconnect clear protected content, invalidate stale callbacks and retain unsent drafts only in page memory, keyed by session and exact question interaction. Returning from the background requires a fresh authoritative hello, including when already locked; an in-progress native ceremony may settle once on its original socket before reconciliation. Pairing and the session link remain intact. Known-success sends clear matching saved drafts, while uncertain sends require inspection rather than automatic retry. Trusted foreground input reports activity at most once per 30 seconds; polling, rendering and programmatic scroll do not renew access.
- **Phone limits:** JavaScriptCore fixtures exercise state transitions, not native Safari user activation, provider prompts, background-page restoration or phone layout. A native credential prompt that never settles on the current socket relies on browser timeout; sensitive Activity log content is deliberately cleared during presentation sealing even with protection off.
- **Mac-only failure diagnostics:** completion receipt, rejected ceremonies and expired-challenge pruning write fixed event/stage/reason codes to the unified log under subsystem `com.repoprompt.app`, category `RemotePasskey`. For a live attempt, note its start/end time and inspect only the app process, for example `log show --last 5m --predicate 'process == "RepoPrompt" AND subsystem == "com.repoprompt.app" AND category == "RemotePasskey"'`; prefer the verified app PID and exact attempt window when other builds run. Tests emit to the same category, so an unfiltered query is not live evidence. Events contain no credential, challenge, origin, identifier or raw error values. A diagnostic-only client-data consistency check runs after an unknown library rejection and never affects acceptance. Phone/MCP errors remain generic; a failed enrollment may require reopening enrollment on the Mac. These diagnostics were added after native 1Password saves succeeded but server enrollment failed. The ensuing diagnosis reproduced a pre-verifier rejection: generic MCP normalization parsed the gateway's JSON-text `credential` into an object, while the provider requires a string. `MCPToolArgsNormalizer` preserves this field for `remote_pairing`; provider and gateway contract fixtures now include that production normalization boundary. On 2026-11-02 the owner confirmed successful registration and separate Unlock on the corrected Dev build in normal iPhone Safari with 1Password. The owner also confirmed background/reconnect/second-tab reuse, cross-tab Lock, draft restoration and Telegram-linked session actions. After roughly an hour with the phone locked, the owner confirmed that protected Safari required unlocking and successfully sent a message afterward; this accepts idle-lock behavior, not a measurement of the exact 30-minute boundary. The owner also revoked stale Brave and old Safari Dev pairings. Guided live checks then confirmed cancellation leaves content hidden and retry succeeds, revoked Brave access is refused, and Mac Reset preserves required protection followed by successful re-enrollment and separate Unlock. A direct HTTP smoke check showed only pairing and no session content; same-identity HTTP passkey refusal was not tested because HTTP and HTTPS have separate browser storage. A distinct unavailable-provider failure remains unverified.
- **Remaining gates:** Step 5 has been deployed with owner approval and has partial live Safari/1Password acceptance; the remaining manual checks are listed above. Unknown extension values remain unused for authorization; nested exotic duplicate keys and the separate unused Codable decoder are not universally qualified. Independent external positive fixtures remain pending.

## Setup (owner-run)
1. In the Tailscale admin console, enable MagicDNS and HTTPS certificates.
2. In Remote Control settings, set Browser link (HTTPS) to 8443 (never 443) and make sure the gateway is running and ready.
3. Run the command Settings shows for the running build: `tailscale serve --bg --https=8443 http://127.0.0.1:<gateway port>`. Live setup used 47392 for Dev; 47391 is the default release port. Check `tailscale serve status` and confirm the 443 configuration is unchanged. One Serve port forwards to one build. After switching builds, re-run the command shown in the build in use.
4. On the iPhone, set Telegram → Privacy and Security → Open Links in → Safari. Open a link in a normal Safari tab, check that the fingerprint matches, and approve pairing on the Mac. A session link opened before pairing opens that session after pairing.

## Recovery
- **Revoked or stale pairing:** tap Forget pairing on the page, then pair again and approve on the Mac.
- **Private Safari tabs** have a separate, isolated identity and ask to pair again. Use a normal tab.
- **Links fail after a build switch:** re-run that build's Serve command.
- **Telegram rejects the URL button:** clear the browser HTTPS port. Alerts go back to text only, and the Serve setup stays in place.
